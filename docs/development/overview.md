# Architecture overview

Dashboard Services Manager (DSM) keeps the YAML config of a self-hosted dashboard (Dashy,
Homepage) in sync with the services running in your infrastructure. Entries added by hand stay
in the file. Two long-lived processes do the work:

- **[Dsm.Provider.App](../../src/Dsm.Provider.App/)** is a console `BackgroundService`,
  usually one per host. It polls one or more sources (Docker, Docker Swarm, Traefik, a YAML
  file) and POSTs what it finds.
- **[Dsm.Manager.Api](../../src/Dsm.Manager.Api/)** is an ASP.NET Core API. It is the only
  process that reads or writes dashboard files.

## Design

Two decisions shape the code.

**DSM only replaces what it wrote.** A dashboard holds more than a list of containers:
external links, and items with no infrastructure behind them. Regenerating the file would lose
them. So every entry DSM writes carries a marker, and a push replaces only DSM's own entries
from the provider sources that sent it. That rule lives in
[the combiner](managers.md#the-combiner). Hand-written entries survive the merge and are
written back as they were read ([managers.md](managers.md#writing-files)).

**One writer.** Providers describe what they see and nothing more; only the manager touches
dashboard files. Any number of providers can push into one manager: one per Docker host, one
per Traefik instance, one for a static YAML file. The manager serializes their writes.

## One push, end to end

```
[Docker / Swarm / Traefik / YAML file]
        │  IServicesProvider.ListServices()
        ▼
Dsm.Provider.App                  every RefreshInterval (default 60 s)
        │  POST /dashboard-services   List<Service> as JSON
        ▼
Dsm.Manager.Api → DashboardCommandProcessor     (one POST at a time)
        │  1. store each source's copies as posted (/data/state.json),
        │     drop sources silent past StaleProviderTimeout
        │  2. merge copies of the same service; drop ignored, URL-less and
        │     IgnoredServiceNames services; apply per-service defaults
        │  3. for each configured dashboard:
        │       read its file → keep hand-written entries → combine
        │       → resolve icons → write if changed
        ▼
Dashy: <dir>/conf.yml        Homepage: <dir>/services.yaml (+ settings.yaml)
```

1. Each provider lists services and stamps them with its `ProviderId`. The worker posts the
   combined list ([providers.md](providers.md)).
2. The manager replaces the stored copies of each ProviderId in the batch, ignored and URL-less
   ones included, and drops sources that haven't posted for `StaleProviderTimeout`
   ([managers.md](managers.md#provider-state), [stale providers](managers.md#stale-providers)).
3. It merges every source's copies of the same service, filters the result, and fills gaps from
   the per-service defaults ([merging sources](managers.md#merging-sources),
   [service-defaults.md](service-defaults.md)).
4. For each dashboard, the manager:
   - replaces its own entries in that dashboard's file with the merged ones, keeping
     hand-written entries ([managers.md](managers.md#the-combiner))
   - resolves icons the way that dashboard renders them ([icons.md](icons.md))
   - writes the file only if its content changed

## The wire contract

[`Service`](../../src/Dsm.Shared/Models/Service.cs) is a record with these fields: `Name`,
`Url`, `Category`, `Icon`, `ImageUrl`, `Hostname`, `Ignore`, `Autogenerated`,
`ServiceDefaultsName`, `ProviderId`. It travels as JSON. The API's responses use camelCase
property names, and request bodies bind without regard to case.

- **`POST /dashboard-services`** takes a list of services. It returns the merged list given to
  each dashboard, keyed by dashboard type (`"Dashy"`, `"Homepage"`), with icons still in
  their unresolved form.
- **`GET /dashboard-services`** returns the merged services DSM knows from the providers (its
  state, not the dashboard files), without hand-written entries.
- **`GET /health`** is the container health check. It's never behind the API key.

Providers and the manager ship and upgrade separately: container images, release binaries
and the Nix package. A provider host may therefore run an older version than the manager.
Changes to `Service` have to stay compatible, so new fields must be optional. The combiner
has a separate path for POSTs without `ProviderId`s because older providers don't send them.

## Configuration

These mechanics are shared by both apps. The settings themselves are documented in
[managers.md](managers.md#configuration) (`ManagerOptions`),
[service-defaults.md](service-defaults.md) (`ServiceDefaultOptions`) and
[providers.md](providers.md#configuration) (`ProviderOptions`).

Sources, later ones winning:

| | Manager API | Provider |
|---|---|---|
| 1 | the host's defaults (`appsettings.json`, …) | the host's defaults (`appsettings.json`, …) |
| 2 | `service-defaults.yaml` next to the binary (required) | |
| 3 | `manager-config.yml` / `.yaml`: relative path, then `/config/` | `provider-config.yml` / `.yaml`: relative path, then `/config/` |
| 4 | `DSM_` environment variables | `DSM_` environment variables |

- YAML files load through
  [`AddNormalizedYamlFile`](../../src/Dsm.Shared/Configuration/NormalizedYamlConfigurationExtensions.cs),
  which strips underscores from keys. `services_providers`, `servicesProviders` and
  `ServicesProviders` all bind to the same setting. Dashes in dictionary keys, such as
  `calibre-web`, are kept.
- Environment variables use the `DSM_` prefix. `__` separates nesting levels and `__0`, `__1`
  index lists: `DSM_ManagerOptions__DashboardManagers__0__DashboardManagerType=Dashy`.
- The YAML files are ordinary .NET configuration, so log levels and Serilog sinks can go in
  them too ([docs/configuration.md](../configuration.md), [docs/loki.md](../loki.md)).
  [`DsmSerilog`](../../src/Dsm.Shared/Logging/DsmSerilog.cs) reads Serilog settings from
  configuration and writes to the console.
- Options are validated at startup. Invalid configuration stops the process with the list of
  problems.

## Build and run

Work from `src/` (the [testing.md](testing.md#running-tests) section explains why `dotnet test`
needs it):

```sh
cd src
dotnet build Dsm.sln

# Manager API on http://localhost:5270 (`--launch-profile https` adds https://localhost:7015).
# It refuses to start without at least one dashboard, so point one at a scratch directory:
DSM_ManagerOptions__DashboardManagers__0__DashboardManagerType=Dashy \
DSM_ManagerOptions__DashboardManagers__0__DashboardConfigDirectoryPath=$(mktemp -d) \
dotnet run --project Dsm.Manager.Api

# A provider pushing to it, here from a YAML file so no Docker is needed:
DSM_ProviderOptions__ApiUrl=http://localhost:5270 \
DSM_ProviderOptions__ServicesProviders__0__ServicesProviderType=YamlFile \
DSM_ProviderOptions__ServicesProviders__0__ServicesYamlFilePath=/path/to/services.yaml \
dotnet run --project Dsm.Provider.App

# The offline test suite
dotnet test --solution Dsm.sln --filter "TestCategory!=Network"
```

In the Development environment the API also serves its OpenAPI document at `/openapi/v1.json`.

**Containers.** [docker-compose/docker-compose.yaml](../../docker-compose/docker-compose.yaml)
runs the published images. Next to it,
[docker-compose.override.yaml](../../docker-compose/docker-compose.override.yaml) adds `build:`
sections for [docker/api.Dockerfile](../../docker/api.Dockerfile) and
[docker/provider.Dockerfile](../../docker/provider.Dockerfile). Compose merges the override
automatically, so this builds and runs the working tree:

```sh
cd docker-compose
docker compose --env-file env up --build -d
```

A deploy host copies only `docker-compose.yaml`, `env`, `manager-config.yaml` and
`provider-config.yaml`, so it never sees the override.

**Releases.** Pushes to `main` and pull requests run the test suite and the Nix checks.
Pushing a version tag (`1.2.3` or `v1.2.3`) also builds and publishes the release
([.github/workflows/ci.yaml](../../.github/workflows/ci.yaml)):

1. Multi-arch images `ghcr.io/andyattebery/dashboard-services-manager:{api,provider}-<version>`.
   They're also tagged `-latest` unless the version is a prerelease.
2. Self-contained single-file binaries of both apps for Linux, macOS and Windows (x64 and
   arm64), attached to a GitHub release.
3. A run of [update-flake.yml](../../.github/workflows/update-flake.yml), which points
   `nix/package.nix` at the new release binaries, verifies the package on every platform it
   supports, and commits the change to `main`.

The [flake](../../flake.nix) packages that released provider binary and provides a NixOS
module ([nix/module.nix](../../nix/module.nix)) that runs it.
