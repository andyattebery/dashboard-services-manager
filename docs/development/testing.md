# Testing

How to run the tests, and the conventions new tests follow.

There are two test projects, [Dsm.Managers.Tests](../../src/Dsm.Managers.Tests/) and
[Dsm.Providers.Tests](../../src/Dsm.Providers.Tests/). Both use NUnit 5 on
Microsoft.Testing.Platform (MTP): `EnableNUnitRunner` turns each one into an executable test
application. Both reference [Dsm.Shared.Tests](../../src/Dsm.Shared.Tests/), a plain library of
shared test infrastructure. It holds no tests itself.

## Running tests

Run `dotnet test` from `src/`:

```sh
cd src
dotnet test --solution Dsm.sln --filter "TestCategory!=Network"    # the suite CI runs
dotnet test --project Dsm.Managers.Tests                            # one project, network tests included
dotnet test --project Dsm.Managers.Tests --filter "FullyQualifiedName~ServicesCombinerTests"   # one fixture
dotnet test --project Dsm.Managers.Tests --filter "Name=AutogeneratedExisting_SameName_SameHostname_IsReplaced"   # one test
```

The directory matters. [src/global.json](../../src/global.json) sets
`"test": { "runner": "Microsoft.Testing.Platform" }`, which puts `dotnet test` in its MTP mode,
and `--solution` and `--project` are options of that mode. The `dotnet` CLI looks for
`global.json` in the current directory and then its parents. From the repository root it never
finds this one, so `dotnet test` stays in VSTest mode and rejects those options with
`MSB1001: Unknown switch`. Any directory under `src/` works.

`TestCategory!=Network` leaves out the tests that call the public icon CDN (see
[Network-dependent tests](#network-dependent-tests)).

## Project layout

Both test projects have the same shape:

```
Dsm.{Managers,Providers}.Tests/
├── {Manager,Provider}TestFixtureHostedTestBase.cs   project defaults for fixture-shared DI (below)
├── Usings.cs                                        global usings: NUnit.Framework, Dsm.Shared.Tests
├── UnitTests/                                       one fixture per file, named <SUT>Tests
└── TestData/                                        static YAML/JSON fixtures, copied to the output directory
```

`Dsm.Managers.Tests` also has [IconHttpClientStubs.cs](../../src/Dsm.Managers.Tests/IconHttpClientStubs.cs)
(see [Mocking and stubs](#mocking-and-stubs)) and
[ManualTimeProvider.cs](../../src/Dsm.Managers.Tests/ManualTimeProvider.cs), a `TimeProvider`
whose timestamps move only when a test calls `Advance`.

Read fixture files with `TestDataUtilities.GetTestDataPath("foo.yml")`. It returns the
relative path `TestData/foo.yml`, which resolves because test runs start in the output
directory, where `TestData/` is copied.

## Shared infrastructure

Everything in `Dsm.Shared.Tests` is in scope in both projects through
`global using Dsm.Shared.Tests;`.

| Type | Purpose |
|---|---|
| [TestHost](../../src/Dsm.Shared.Tests/TestHost.cs) | `TestHost.Create(configureConfiguration, configureServices)` builds a disposable `IHost` with DSM's Serilog setup. |
| [TestFixtureHostedTestBase](../../src/Dsm.Shared.Tests/TestFixtureHostedTestBase.cs) | Base class for fixture-shared DI. Builds one host in `[OneTimeSetUp]`, exposes it as `ServiceProvider`, and disposes it in `[OneTimeTearDown]`. |
| [PerTestHostedTestBase](../../src/Dsm.Shared.Tests/PerTestHostedTestBase.cs) | Base class for per-test DI. `CreateHost(...)` builds a host that is disposed in `[TearDown]`. A test can create several; they are disposed in reverse order. |
| [TestTempDir](../../src/Dsm.Shared.Tests/TestTempDir.cs) | Disposable scratch directory (see [Filesystem fixtures](#filesystem-fixtures)). |
| [TestTimeouts](../../src/Dsm.Shared.Tests/TestTimeouts.cs) | `HungThresholdMs` for `[CancelAfter]` (see [Hung tests](#hung-tests)). |
| [TestDataUtilities](../../src/Dsm.Shared.Tests/TestDataUtilities.cs) | Path helper for `TestData/` files. |

## Hosting the code under test

Choose by asking whether the DI graph differs between the tests in a fixture.

**The same graph for every test: extend the project's fixture base.** A fixture extends
`ManagerTestFixtureHostedTestBase` or `ProviderTestFixtureHostedTestBase`. Each subclasses
`TestFixtureHostedTestBase` and registers the project's real services:

- `ManagerTestFixtureHostedTestBase`: `AddDsmManagerServices()` and
  `ConfigureOfflineIconHttpClients()`, plus the configuration from `AddDsmManagerConfiguration()`.
  That configuration includes the shipped `service-defaults.yaml`.
- `ProviderTestFixtureHostedTestBase`: `AddDsmProviderServices()`.

Override `AddServices` to add test doubles. Call `base.AddServices(services)` first to keep the
defaults.

```csharp
[CancelAfter(TestTimeouts.HungThresholdMs)]
public class FooTests : ProviderTestFixtureHostedTestBase
{
    [Test]
    public async Task ListServices_ReturnsLabelledContainers()
    {
        var sut = ServiceProvider.GetRequiredService<MyService>();
        // ...
    }

    protected override void AddServices(IServiceCollection services)
    {
        base.AddServices(services);
        services.AddTransient<IFoo>(_ => new FakeFoo());
    }
}
```

Examples: [DockerServicesProviderTests](../../src/Dsm.Providers.Tests/UnitTests/DockerServicesProviderTests.cs),
[ServiceFactoryTests](../../src/Dsm.Managers.Tests/UnitTests/ServiceFactoryTests.cs).

**A graph that depends on the test: extend `PerTestHostedTestBase`.** Build the host inside the
test, usually in a small fixture-specific helper. Use this when each test needs its own options
or its own temp directory.

```csharp
[CancelAfter(TestTimeouts.HungThresholdMs)]
public class FooTests : PerTestHostedTestBase
{
    [Test]
    public async Task WriteServices_CreatesFile()
    {
        using var dir = TestTempDir.Create("dsm_foo");
        var sut = BuildService(dir.Path);
        // ...
    }

    private MyService BuildService(string configDirectory)
    {
        var host = CreateHost(configureServices: services =>
        {
            services.AddDsmManagerServices();
            services.ConfigureOfflineIconHttpClients();
            services.Configure<ManagerOptions>(opts => { /* per-test config */ });
        });
        return host.Services.GetRequiredService<MyService>();
    }
}
```

Examples: [DashboardCommandProcessorTests](../../src/Dsm.Managers.Tests/UnitTests/DashboardCommandProcessorTests.cs),
[DashyDashboardManagerTests](../../src/Dsm.Managers.Tests/UnitTests/DashyDashboardManagerTests.cs),
[HomepageDashboardManagerWidgetMatchingTests](../../src/Dsm.Managers.Tests/UnitTests/HomepageDashboardManagerWidgetMatchingTests.cs).

For a single test that fits neither base, build the host inline:
`using var host = TestHost.Create(configureServices: ...);`.

**No DI at all.** Pure transformations and parsers are easier to construct by hand:
[ServicesCombinerTests](../../src/Dsm.Managers.Tests/UnitTests/ServicesCombinerTests.cs),
[TraefikRuleParserTests](../../src/Dsm.Providers.Tests/UnitTests/TraefikRuleParserTests.cs),
the options-validator tests. So is a SUT whose side effects you would otherwise suppress by
overriding registrations. [HomepageSettingsLayoutTests](../../src/Dsm.Managers.Tests/UnitTests/HomepageSettingsLayoutTests.cs)
builds `HomepageDashboardManager` with `NullLogger` and a stub icon source.

## Mocking and stubs

The two projects follow different conventions, because their dependencies have different
shapes.

**`Dsm.Providers.Tests` uses Moq** for the outer edges: `IDockerClient`, `ITraefikApiClient`
and `ITraefikApiClientFactory`. The mocks return the JSON fixtures in `TestData/`, and the rest
of the graph is real DI. This is why the provider suite needs neither a Docker daemon nor a
Traefik instance. Examples:
[DockerServicesProviderTests](../../src/Dsm.Providers.Tests/UnitTests/DockerServicesProviderTests.cs),
[TraefikServicesProviderTests](../../src/Dsm.Providers.Tests/UnitTests/TraefikServicesProviderTests.cs).
Because those mocks stand in for the Refit clients,
[RefitClientTests](../../src/Dsm.Providers.Tests/UnitTests/RefitClientTests.cs) builds the
real ones against a stub `HttpMessageHandler`.

**`Dsm.Managers.Tests` uses hand-rolled stubs and doesn't reference Moq.** Manager code is
mostly data transformation with a shallow collaborator graph. A small
`sealed class StubIconSource : IDashboardIconSource` reads more clearly than a `Mock<>` setup.
Examples are `StubIconSource` in
[HomepageSettingsLayoutTests](../../src/Dsm.Managers.Tests/UnitTests/HomepageSettingsLayoutTests.cs)
and `StubDashboardManager` in
[IconResolverTests](../../src/Dsm.Managers.Tests/UnitTests/IconResolverTests.cs). If a manager
test needs so much setup that stubs get noisy, the code under test is probably doing too much.
Refactor it before reaching for Moq.

**Icon CDN calls are stubbed by default.** `services.ConfigureOfflineIconHttpClients()`
([IconHttpClientStubs.cs](../../src/Dsm.Managers.Tests/IconHttpClientStubs.cs)) swaps the
handler on each icon source's named `HttpClient` for one that answers `200 OK`. That keeps
manager tests offline while the real `service-defaults.yaml` fallback chain stays in play.
`ManagerTestFixtureHostedTestBase` calls it. Per-test hosts that register
`AddDsmManagerServices()` call it themselves. `IconResolverTests` overrides `AddServices` to
leave it out, because its `[Category("Network")]` tests need the real CDN. The stub lists the
icon sources by client name, so a new icon source has to be added there too (see
[icons.md](icons.md#adding-an-icon-source)).

## Filesystem fixtures

Use [`TestTempDir.Create("prefix")`](../../src/Dsm.Shared.Tests/TestTempDir.cs). It creates
`<temp>/prefix_<guid>`, exposes `Path` and `RootedPath(relative)`, and deletes the directory
recursively on `Dispose`. Use `using var` in a test, or a field disposed in `[TearDown]`.

Avoid hand-rolled `Path.GetTempPath()` + `Directory.CreateDirectory` setups. They leak
directories when a test fails, and they hide which test owns which files.

## Network-dependent tests

A test that reaches a public host must be tagged `[Category("Network")]`. The only public host
DSM calls is `cdn.jsdelivr.net`, which the icon sources probe. That's why
`--filter "TestCategory!=Network"` gives an offline run.

[IconResolverTests](../../src/Dsm.Managers.Tests/UnitTests/IconResolverTests.cs) is the
reference: it mixes tagged and untagged tests depending on whether the path under test reaches
the CDN. Tag any new test that calls `JsDelivrIconSource`, or any other `IDashboardIconSource`
whose `HttpClient` talks to a real host.

## Hung tests

Every fixture class carries `[CancelAfter(TestTimeouts.HungThresholdMs)]` (30 s). The attribute
is cooperative. When the time is up, NUnit cancels the test's `CancellationToken`, which a test
receives as an extra method parameter or through `TestContext.CurrentContext.CancellationToken`.
Nothing is interrupted unless that token reaches the code that is running. The DSM calls that do
I/O (`ListServices()`, `WriteServices()`, `GetIconUrl(...)`) take no token.

Put the attribute on each fixture class. The convention dates from NUnit 4.5.1, where
`CancelAfterAttribute` was declared `Inherited = false` and didn't reach derived fixtures.
NUnit 5.0.0 declares it `Inherited = true` (checked by reflection), so a base-class attribute
would now reach them too. The fixtures still carry their own.

## Naming

- Leave out `[TestFixture]`; NUnit detects fixtures from their `[Test]` methods. A new fixture
  starts with `[CancelAfter(TestTimeouts.HungThresholdMs)]` directly above
  `public class FooTests`.
- Test methods are named `MethodOrScenario_Condition_ExpectedResult` in PascalCase, for example
  `NativePrefix_PassesThroughWithoutTranslation`, `SameHostname_SameProviderId_IncomingReplaces`.
  A failing CI line shows only the method name, so the name has to identify the scenario.

## What "green" means

- The non-network suite (`dotnet test --solution Dsm.sln --filter "TestCategory!=Network"` from
  `src/`) is the contract for offline correctness and must always pass. It is what CI runs.
- Network-tagged tests may fail when the CDN is unreachable. Failures in the smoke list
  `IconResolverTests.FallbackChain_HomarrLabsIcons_Smoke` (rate limits, transient 403s) reflect
  upstream availability, not a regression.
