# Configuring the manager

The manager keeps one or more dashboard YAML config files in sync. Pick which dashboards it
manages, where their config files live on disk, and any per-service defaults you want, all in
[`manager-config.yaml`](../docker-compose/manager-config.yaml).

## What the manager writes

For every service the providers post, the manager:

1. Keeps each source's latest copies, ignored ones and ones without a URL included, in its state
   (see [Manager state](#manager-state)).
2. Merges the copies different sources post for the same service (see
   [Two sources, one service](providers.md#two-sources-one-service)), then drops anything ignored,
   without a URL, or named in `IgnoredServiceNames`.
3. Applies per-service defaults — adding an icon, category, or hostname-templated name — from
   the shipped defaults plus your overrides.
4. For each configured dashboard, reads the existing file, keeps anything you typed by hand,
   replaces its own entries with the merged ones, and writes the result back. Identical content is
   **not** rewritten, so dashboards that watch the file don't reload spuriously.

`GET /dashboard-services` returns the same merged services: what the manager knows from the
providers, without your hand-written entries.

The merge rule is the load-bearing one: anything the manager didn't put there itself stays put.
You can hand-edit your dashboard YAML and the manager won't touch your changes — it only
replaces entries it owns. It also removes entries it owns once their provider source has stopped
posting for long enough; see
[Services from providers that stop posting](#services-from-providers-that-stop-posting).

## Dashboard backends

### Dashy

```yaml
- DashboardManagerType: Dashy
  DashboardConfigDirectoryPath: /dashy_config       # writes /dashy_config/conf.yml
```

The manager rewrites only the `sections:` block. Everything else in the file (`appConfig`,
`pageInfo`, theme overrides, etc.) is preserved. Within `sections:` it rebuilds only its own
items. Your items are left exactly as you wrote them, and so are a section's own settings
(`displayData`, …). The one exception: if a category has an icon configured (see
[Per-service defaults](#per-service-defaults)), that icon replaces the section's. Auto-generated
items get an `_autogenerated` tag plus a `host=<hostname>` tag, so you can spot them in the UI:

```yaml
items:
  - title: Jellyfin
    url: https://jellyfin.example
    tags:
      - _autogenerated
      - host=media-01
```

If you remove the `_autogenerated` tag from an entry, the manager treats it as user-owned from
that point on — re-runs of the provider won't replace it, and it isn't removed when its provider
stops posting.

### Homepage

```yaml
- DashboardManagerType: Homepage
  DashboardConfigDirectoryPath: /homepage_config    # writes /homepage_config/services.yaml
```

The manager rewrites `<dir>/services.yaml` and updates `<dir>/settings.yaml` with category
icons (non-icon settings — theme, providers, layout columns, etc. — are preserved). In
`services.yaml` it rebuilds only its own entries. Your entries are left exactly as you wrote
them, `description`, `widget` and all.
Auto-generated entries are marked with a custom `_autogenerated: true` field that Homepage
ignores but the manager uses on the next run:

```yaml
- Media:
    - Jellyfin:
        href: https://jellyfin.example.com
        icon: jellyfin.png
        server: media-01
        _autogenerated: true
```

Removing `_autogenerated: true` from an entry does the same thing as removing the tag in
Dashy: the entry becomes user-owned and is preserved going forward.

## Status monitoring

Per-dashboard flag — when on, every entry the manager generates gets the dashboard's
status-ping directive. Entries you wrote by hand are left alone; add the directive to them
yourself if you want it.

```yaml
- DashboardManagerType: Homepage
  DashboardConfigDirectoryPath: /homepage_config
  EnableStatusMonitoring: true
```

| Dashboard | What gets emitted |
|---|---|
| Dashy | `statusCheck: true` per item ([Dashy status indicators](https://dashy.to/docs/status-indicators)) |
| Homepage | `siteMonitor: <href>` per entry ([Homepage site monitor](https://gethomepage.dev/configs/services/#site-monitor)) |

For Homepage specifically: if a service has a widget attached (see below), `siteMonitor` is
suppressed for that entry — widgets do their own polling and emitting both would be redundant.

## Homepage service widgets

Optional. Point `SourceHomepageServiceWidgetsFilePath` at a YAML file in
[Homepage's service-widgets format](https://gethomepage.dev/configs/service-widgets/) and the
manager will merge the matching widget into each service entry it generates. A hand-written
entry keeps its own inline `widget:` instead.

```yaml
- DashboardManagerType: Homepage
  DashboardConfigDirectoryPath: /homepage_config
  SourceHomepageServiceWidgetsFilePath: /homepage_config/widgets.yaml
```

A widgets file with three AdGuard Home instances on different hosts, plus an unscoped Immich
widget:

```yaml
- adguardhome:
    server: network-01
    widget:
      type: adguard
      url: https://adguardhome.example
      username: "{{ network_01_adguardhome_username }}"
      password: "{{ network_01_adguardhome_password }}"
- adguardhome:
    server: pi-rack
    widget:
      type: adguard
      url: https://adguardhome-02.example
- adguardhome:
    server: network-03
    widget:
      type: adguard
      url: https://adguardhome-03.example
- immich:
    widget:
      type: immich
      url: https://immich.example
      key: ...
```

Match precedence (case-insensitive on both sides):

1. **Service name + hostname** — top-level key matches the service name and `server:` matches
   the host the service runs on.
2. **Default service name + hostname** — for services renamed by a hostname-templated name
   (e.g. `adguardhome` → `AdGuard Home (network-01)`), the widget can still key off the
   original short name. Combined with `server:`, this lets one widgets file map cleanly to
   multiple hosts running the same service.
3. **Service name only** — widget without `server:`, used when the hostname doesn't match any
   server-scoped entry.
4. **Default service name only** — final fallback.

Widgets without a `server:` work as a catch-all for any host that doesn't have a more specific
match.

## Per-service defaults

DSM ships with a default set of category mappings, name templates, and per-service overrides
for popular self-hosted apps (Plex, AdGuard Home, Traefik, Proxmox, etc.). Most services also
get an icon picked automatically based on their name — see [icons.md](icons.md) for the full
icon story. Override or extend the shipped defaults in `manager-config.yaml` under
`ServiceDefaultOptions`:

```yaml
ServiceDefaultOptions:
  Categories:
    media:    { Icon: mdi-multimedia }
    network:  { Icon: mdi-network }
    ai:       { Name: AI, Icon: mdi-assistant }     # Name overrides the auto-title-cased key
  Services:
    plex:
      Icon: my-custom-plex-icon         # overrides the auto-pick for plex
    my-internal-tool:
      Category: utilities
      ImagePath: /assets/logo.svg       # resolved against the service URL
```

Per-field rule: anything the provider sent wins; defaults fill in the gaps. Removing a default
means setting the corresponding key blank — the merge is leaf-level, so unrelated keys inside
the same service entry survive your override.

## Ignored services

Some service names should never appear on a dashboard — typically the manager itself, or other
infrastructure services that the provider scrapes from a container label even though you don't
want them surfaced.

```yaml
ManagerOptions:
  IgnoredServiceNames:
    - Dashboard Services Manager
    - Dashy
    - Homepage
```

Comparison is case-insensitive against the service name.

## Services from providers that stop posting

Each provider source (one `ServicesProviders` entry on one host) posts its services every
refresh. A source can stop posting because you removed it from a provider's config, its host is
gone, or it keeps failing. At first the manager can't tell which, so it keeps that source's
entries. Once the source has gone `StaleProviderTimeout` without posting, the manager removes them:

```yaml
ManagerOptions:
  StaleProviderTimeout: 01:00:00    # the default; [d.]hh:mm:ss, must be positive
```

- The check runs whenever any provider posts, so the entries go on the first post after the
  timeout passes.
- Keep the timeout well above every provider's `RefreshInterval`. A shorter one removes a
  provider's entries between its posts, and they reappear on the next one.
- A source that comes back is added again on its next post.
- A host that stays down longer than the timeout drops off the dashboard, status indicator
  included, until it posts again. Raise the timeout if you'd rather keep showing it.
- Restarting the manager restarts the timeout. So does a stretch with no posts from any provider
  at all, which points at the manager's own network rather than at every provider.
- Changing a provider's hostname, or how many sources of one type it has, gives its sources new
  IDs (see [Provider identity](providers.md#provider-identity)). Entries under an old ID are
  removed the same way.
- Entries you've made your own (no `_autogenerated`) are never removed.

## Manager state

The manager keeps every source's latest services in `/data/state.json` inside its container.
That's how it remembers what a dashboard never shows: an ignored container, or one without a URL
whose labels apply to another source's copy. Mount a directory there:

```yaml
volumes:
  - ./data:/data
```

- Without a mount, the state lives in an anonymous Docker volume. It survives restarts and
  `docker compose up`, but is lost when the container is removed.
- If the state is lost, then until each source posts again (one refresh interval), an ignored
  service can briefly reappear, or a label value briefly go missing.
- With no state file yet (first start, or after losing it), the manager rebuilds the state from
  the first configured dashboard's file. Nothing disappears while the providers report in.
- Outside Docker, if `/data` doesn't exist, the state stays in memory and the manager logs a
  warning.

## Multiple dashboards

You can configure several `DashboardManagers` entries — one per dashboard target. The manager
writes the same merged service list into each, independently:

```yaml
ManagerOptions:
  DashboardManagers:
    - DashboardManagerType: Dashy
      DashboardConfigDirectoryPath: /dashy_config
    - DashboardManagerType: Homepage
      DashboardConfigDirectoryPath: /homepage_config
      EnableStatusMonitoring: true
```

Two of the same `DashboardManagerType` is **not** supported — the manager fails fast at
startup if it sees a duplicate.
